# Roadmap

Status: **R3 deployed (2026-11-18).** Live dashboard:
https://dataops-dashboard-wbmpiyks3q-uc.a.run.app. Releases are sequential and each one
ends at an explicit approval gate — no release starts without the previous gate.

Effort is expressed in focused hours and assumes one developer. At 12 h/week the project
takes 14–18 weeks; at 20 h/week, 8–11 weeks; full time, 4–6 weeks.

---

## 1. Release model

| Release | Theme | Effort | Gate |
|---|---|---|---|
| **R0** | Foundation: docs + scaffold | 30–40 h | CI green locally; docs reviewed |
| **R1** | Deterministic core | 70–90 h | Normal vs failure demo with anomaly + incident |
| **R2** | AI + interface | 40–55 h | Evidence-grounded diagnosis + public dashboard |
| **R3** | Cloud + portfolio | 25–35 h | Reproducible deploy, demo assets, final review |
| **Total** | | **165–220 h** | |

Each release must leave the repository in a coherent, demonstrable state. If work stops after
R1, the project still tells a complete story (observability + quality + anomalies). R2 and R3
add the AI narrative and the public artifact.

## 3. R1 — Deterministic core (complete)

**Goal:** run a realistic pipeline and explain what went wrong without any LLM.

**Delivered:** 2026-11-18. Labelled demo (45 days = 16 incidents; 90 days = 24) in under a
minute; 160 tests; 90.4% statement coverage; `ruff` and `mypy --strict` clean. Backtest:
**precision 1.00, recall 1.00** on 24 injected incidents (3 per family), 0 false-positive
days, mean detection delay 0 days (synthetic data).

### 3.1 Demo pipeline (20–28 h)

- `sales_raw` ingestion from seeded synthetic CSVs (scenario + seed parameters).
- Cleaning to `sales_clean` with explicit rejection reasons (never silently dropped).
- Aggregation to `sales_daily_metrics`.
- Configurable backfill command (45 days for the demo, 90 supported).
- Nine scenarios: normal, ingestion_failure, volume_drop, duplicate_spike, null_spike,
  schema_change, price_anomaly, slow_run, stale_data.
- Determinism test: same seed + scenario → identical row counts and hash.

### 3.2 Instrumentation (10–14 h)

- Execution context emitting `pipeline_executions`, `execution_steps`, `metric_observations`.
- Counters for read/processed/rejected; terminal status guaranteed via `finally`.
- Stale-run reaper.
- Idempotent re-run of the same logical date.

### 3.3 Quality engine (24–32 h)

- YAML catalog, validator, SQL compiler, executor, result writer, score aggregation.
- Nine rule types (`not_null`, `unique`, `accepted_values`, `regex_match`, `range`,
  `expression`, `foreign_key`, `freshness`, `schema_contract`).
- Rule versioning and 7-dimension score.
- Fixtures for every dimension.

### 3.4 Anomaly engine + correlation (28–40 h)

- Detectors D1–D7, history tiers, severity model.
- Correlation into incidents with evidence links and dedup.
- Backtest over the labelled window with precision/recall report.
- Scenario labels persisted with each execution (no hidden ground truth).

**Exit criteria**

- [x] A normal run produces zero `high`+ anomalies over 30 consecutive simulated days.
- [x] Each injected scenario produces the expected signal type, severity and incident scope.
- [x] Backtest report generated by one command, with recall ≥ 0.80 and precision ≥ 0.85.
- [x] Re-running any date produces no duplicate rows (covered by the idempotency tests).
- [x] One incident per injected day; 24/24 incidents in the 90-day benchmark (no alert fan-out).

**Demo checkpoint:** terminal cast showing a normal run, then `volume_drop`, then the incident
with correlated signals — no AI involved.

## 4. R2 — AI and interface (complete)

**Goal:** a public, investigation-oriented dashboard with evidence-grounded diagnoses.

**Delivered:** 2026-11-18. 24 incidents from a 90-day labelled history; 24/24 schema-valid
diagnoses; evidence groundedness 100%; strict cause-category accuracy 100% (candidate-assisted,
documented); ~US$ 0.003 per diagnosis; 4.3 s average latency; prompt-injection probe passed.
Streamlit dashboard over a JSON snapshot, no warehouse access from the UI. 174 tests, 87.3%
coverage.

### 4.1 Diagnosis service (16–24 h)

- Evidence bundle builder with budget and canonical hashing.
- Prompt v1 + JSON schema + Pydantic models.
- Vertex AI provider + `FakeDiagnosisProvider`.
- Validation pipeline (schema, evidence IDs, numeric presence, confidence rules).
- Dedup, severity gate, budget cap, kill switch.
- Golden set (20–30 incidents) and evaluation script.
- Adversarial prompt-injection tests.

### 4.2 Dashboard (16–20 h)

- Seven pages: Overview, Pipelines, Data Quality, Anomalies, Incidents, AI Diagnosis, Operations.
- Snapshot loader (Parquet + manifest) with cache and last-good fallback.
- Fact vs hypothesis rendering; evidence IDs linked to the timeline.
- Empty/degraded states (a broken snapshot must be visible, not hidden).
- Local mode reading the same snapshot format.

**Exit criteria**

- Golden set metrics published: cause accuracy ≥ 0.70, groundedness ≥ 0.95, invalid rate
  < 5%, refusal correctness ≥ 0.90.
- No diagnosis without a cited evidence ID; validation rejects invented IDs in tests.
- Dashboard renders all seven pages from a snapshot with BigQuery disabled.
- Page load does not issue any warehouse query (verified by test double).

**Demo checkpoint:** incident detail → diagnosis → recommendations, with a clear visual
separation between computed and generated content.

## 5. R3 — Cloud and portfolio (deployed)

**Goal:** deploy from zero with Terraform, operate it cheaply, and present it well.

**Delivered:** 2026-11-18. BigQuery adapter (MERGE, load jobs, partitioned/clustered DDL),
Terraform for APIs/IAM/Artifact Registry/GCS/BigQuery/Cloud Run Job/Cloud Run Service/
Scheduler/WIF, multi-purpose image, CI Terraform validation, manual deploy workflow,
runbook, live screenshots and a public URL.

**Deployed state:** 33 days of BigQuery history, 13 incidents and 13 Gemini diagnoses;
daily run validated end to end (pipeline → quality → detection → correlation → diagnosis →
snapshot upload) in 3m32s; AI spend US$ 0.042. Budget alerts could not be created because
the Billing Budgets API returned `INVALID_ARGUMENT`; the Terraform resource remains ready.

### 5.1 Infrastructure (12–16 h)

- Terraform: APIs, BigQuery datasets/tables/views, bucket + lifecycle, Artifact Registry,
  service accounts + IAM, Cloud Run Job, Cloud Run service, Scheduler, budget alerts.
- Remote state in GCS (versioned, not committed).
- `terraform plan` in CI; apply only via manual approval.

### 5.2 CI/CD (6–8 h)

- Workload Identity Federation (no keys), branch-restricted.
- Build → push → deploy job (manual environment approval).
- Terraform fmt/validate/plan; docs link check.

### 5.3 Operations and demo assets (7–11 h)

- Runbook: provision, deploy, run manual stage, inspect logs, rotate, destroy.
- Log-based metrics and alert policies.
- Screenshots, architecture diagram, 3–5 minute demo script/video.
- Final README with measured results, limitations and cost.

**Exit criteria**

- [x] Terraform configuration validates and covers every approved service.
- [x] BigQuery adapter and DDL implemented and unit-tested (live smoke pending apply).
- [x] CI validates Terraform; deploy workflow builds two images and rolls them out.
- [x] Runbook documents provision, seed, operate and destroy.
- [x] `terraform apply` executed and the stack verified end to end.
- [x] Public dashboard reachable without authentication; snapshot served from GCS.
- [x] Daily job path validated manually (scheduler trigger configured for 06:00).
- [ ] Seven consecutive unattended days and a final billing check (observation period).
- [ ] Budget alerts configured (blocked by the Billing Budgets API; manual fallback).

## 8. Deferred backlog (explicitly not scheduled)

| Item | Why deferred |
|---|---|
| dbt models + tests | Already demonstrated in the PNCP project; adds a second test semantics |
| Great Expectations adapter | Extension point documented; no v1 need |
| Cloud Workflows | CLI orchestration is sufficient and testable locally |
| Streaming / Pub/Sub | Different problem class; latency and cost |
| ML detectors (STL, isolation forest) | No demonstrated gap versus robust stats |
| Alert channels (Slack/email) | Portfolio audience is the dashboard, not an on-call rotation |
| Multi-tenant / SSO | Out of scope for a demo |
| Automatic remediation | Explicitly forbidden by design |

## 9. Definition of done (all releases)

1. Tests pass locally and in CI; new behaviour has tests.
2. Lint, format and type checks clean.
3. Docs updated in the same change as the code.
4. No credentials, project IDs or personal data committed.
5. Cost impact stated when a new service or query pattern is introduced.
6. `README` status line reflects reality.
7. Demo remains runnable offline.

| Risk | Impact | Mitigation | Owner |
|---|---|---|---|

| LLM evaluation is subjective | Credibility | Deterministic groundedness + small manual review | Author |
| GCP billing surprises | Cost | Budget alerts, bytes cap, snapshot dashboard, teardown | Author |
